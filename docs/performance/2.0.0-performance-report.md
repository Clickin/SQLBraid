# SQLBraid 2.0.0 성능 측정 결과

이 문서는 2026년 10월 19일에 저장한 측정 결과를 한국어로 다시 정리한 보고서입니다. 이번 문서 수정에서는 벤치마크를 새로 실행하지 않았습니다.

## 1. 결론

**SQLBraid는 pg를 직접 호출하는 것보다 처리 비용이 더 듭니다. 이번 최적화로 그 비용의 일부를 줄였습니다.** 다만 SQLBraid가 모든 비교 라이브러리보다 빠르다거나, 모든 실제 쿼리가 같은 비율로 빨라졌다는 결과는 아닙니다.

확인한 내용은 다음과 같습니다.

- 쿼리마다 발생하는 비용 중에서는 **사용하지 않는 옵저버 이벤트를 만드는 작업**을 줄였습니다. 옵저버는 쿼리 실행을 관찰하는 로깅·감사·계측용 콜백입니다.
- 많은 행을 읽을 때는 **각 셀마다 같은 PostgreSQL 타입명을 정리하는 작업**이 반복됐습니다. 이미 정해진 이름은 다시 정리하지 않도록 바꿨습니다.
- 두 변경은 DB 통신을 제외한 실험에서 효과가 반복해서 나타났습니다. 타입명 처리 변경은 실제 PostgreSQL의 대량 조회에서도 효과가 있었습니다.
- 작은 실제 쿼리는 DB 통신과 실행 시간의 편차 때문에 개선 여부를 명확하게 판단하기 어려웠습니다.

**아래에서 ‘다른 라이브러리와의 비교’와 ‘SQLBraid 자체의 최적화 전후 비교’를 구분해서 읽어야 합니다.** 전자는 현재 상대적인 위치를 보여주고, 후자는 코드 변경의 효과를 확인합니다.

## 2. 다른 라이브러리와 비교하면 어느 정도인가요?

다음 표는 **최적화 후** 전체 측정 결과입니다. 각 라이브러리가 pg를 직접 호출했을 때보다 시간이 얼마나 더 걸렸는지 나타냅니다. 낮을수록 pg에 가깝습니다.

| 비교 방식                                           |      SQLBraid |          UQL |       Kysely |       Drizzle |
| --------------------------------------------------- | ------------: | -----------: | -----------: | ------------: |
| 각 라이브러리의 일반적인 API로 같은 결과 조회       | 24.6% 더 걸림 | 5.3% 더 걸림 | 3.1% 더 걸림 | 24.3% 더 걸림 |
| 같은 SQL을 각 라이브러리의 직접 SQL 실행 API로 실행 | 13.9% 더 걸림 | 2.2% 더 걸림 | 1.2% 더 걸림 |  0.6% 더 걸림 |

표는 조회 형태 14가지에서 각각 `라이브러리 실행 시간 ÷ pg 실행 시간`을 계산한 뒤, 그 14개 비율의 중앙값을 구한 것입니다. 실제 서비스에서 자주 쓰는 쿼리에 가중치를 준 결과는 아닙니다.

두 행이 다른 이유는 실행하는 작업이 다르기 때문입니다. 첫 번째는 쿼리를 구성하고 결과를 객체로 바꾸는 각 라이브러리의 일반적인 사용 비용을 포함합니다. 두 번째는 같은 SQL을 직접 실행하는 경로를 비교합니다. Drizzle의 두 수치가 크게 다른 것도 이런 차이를 반영합니다.

시간의 크기를 가늠할 예도 있습니다. 같은 SQL로 기본 키를 조회해 1행·2열을 가져온 최종 측정에서, pg는 약 **0.087ms**, SQLBraid는 약 **0.098ms**였습니다. 전체 응답 시간의 차이는 약 **0.011ms**였습니다. 이 차이를 전부 SQLBraid 내부 처리 시간으로 단정할 수는 없습니다.

이 표는 최종 3회 측정의 상대적인 위치입니다. 최적화 전의 별도 측정과 수치만 빼서 개선 효과를 계산하지 않았습니다. 개선 효과는 다음 절의 교대 실행 실험으로 판단했습니다.

## 3. 이번 최적화로 무엇이 줄었나요?

### 변경 A: 옵저버가 없으면 성공 이벤트를 만들지 않습니다

기존에는 옵저버가 하나도 없어도 이벤트용 객체와 파라미터 배열을 만든 뒤 버렸습니다. 이제 옵저버가 없는 경우에는 이 작업을 생략합니다.

아래는 **DB 통신 없이 SQLBraid 실행 경로만 측정한 결과**입니다. `µs`는 마이크로초이며, **1,000µs = 1ms**입니다.

| 파라미터 수 |  변경 전 |  변경 후 | 실행 시간 감소 | 빨라진 비교 횟수 |
| ----------- | -------: | -------: | -------------: | ---------------: |
| 1개         |  4.258µs |  3.487µs |          18.3% |       7회 중 7회 |
| 10개        |  7.732µs |  6.478µs |          16.2% |       7회 중 7회 |
| 50개        | 21.884µs | 19.125µs |          13.7% |       7회 중 7회 |

**18.3%라는 수치는 실제 DB 쿼리 전체가 18.3% 빨라졌다는 뜻이 아닙니다.** 이 실험에서는 네트워크와 DB 실행을 제외했습니다. 실제 PostgreSQL의 작은 쿼리에서는 전체 응답 시간의 개선을 확정하지 못했습니다.

옵저버가 있는 경우에는 기존처럼 이벤트를 만듭니다. 아무 작업도 하지 않는 옵저버 하나를 붙인 비교에서는 일관된 개선이나 악화를 확인하지 못했습니다.

변경 위치는 [런타임 준비 단계](../../packages/runtime/src/index.ts)와 [결과 처리 단계](../../packages/runtime/src/operations/materialized.ts)입니다. 파라미터 검사, 결과 종류 검사, 행 개수 검사, 스키마 검증, 오류 전달은 그대로 유지했습니다.

### 변경 B: 이미 정리된 PostgreSQL 타입명은 다시 정리하지 않습니다

기존에는 결과의 각 셀을 처리할 때 타입명에 공백 제거, 소문자 변환, `pg_catalog.` 접두사 제거를 반복했습니다. 예를 들어 이미 `int8`인 이름에도 같은 작업을 수행했습니다.

이제 [기존 타입 목록](../../packages/postgres/src/type-policy.ts)에 있는 이름은 바로 사용합니다. 대문자·공백·접두사가 있는 이름은 기존 방식으로 처리합니다. 임의의 타입명을 계속 저장하는 캐시는 추가하지 않았습니다.

| 측정 대상                                           |  변경 전 |  변경 후 | 실행 시간 감소 | 빨라진 비교 횟수 |
| --------------------------------------------------- | -------: | -------: | -------------: | ---------------: |
| DB 통신 제외, 1,000행 × 32열                        |  1.323ms |  1.181ms |          10.3% |       7회 중 7회 |
| DB 통신 제외, 10,000행 × 32열                       | 13.341ms | 11.590ms |          12.5% |       7회 중 7회 |
| 실제 PostgreSQL, 같은 SQL로 10,000행 × 31열 조회    | 40.355ms | 38.727ms |           4.0% |       7회 중 7회 |
| 실제 PostgreSQL, 10,000행 조회 후 스키마 검증       | 20.331ms | 18.931ms |           6.8% |       7회 중 7회 |
| 실제 PostgreSQL, 기본 무손실 표현으로 10,000행 조회 | 13.534ms | 12.983ms |           2.1% |       7회 중 6회 |

마지막 행은 편차가 컸습니다. 어떤 비교에서는 빨라졌지만, 다른 비교에서는 약 10.5% 더 오래 걸렸습니다. 따라서 기본 무손실 표현에서 항상 2.1% 빨라진다고 주장하지 않습니다.

이 실험에서는 변경 A를 양쪽 빌드에 똑같이 적용했습니다. 따라서 표는 변경 B의 추가 효과를 비교한 것입니다.

두 표의 시간은 **회차별 평균 시간의 중앙값**입니다. 감소율은 **같은 회차의 변경 전후 비율을 구한 뒤 그 비율의 중앙값**으로 계산했습니다. 표시된 두 시간을 직접 나눈 값과 감소율이 조금 다를 수 있습니다.

### 변경 C·D: 후속 최적화 (UQL·Kysely 대비 차이 분석 후)

최종 측정에서 SQLBraid는 큰 결과(31열 × 10,000행)에서 pg보다 21~~30%, 작은 쿼리에서 12~~30% 더 걸렸습니다. UQL·Kysely는 같은 항목에서 대체로 0~12%였습니다. 이 차이는 두 곳에서 나왔습니다. 두 곳 모두 CPU 프로파일로 확인한 뒤 고쳤습니다.

| 변경                                                                                                                                   | 측정 대상                                   | 변경 전 | 변경 후 | 시간 감소 | 빨라진 비교 횟수 |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ------: | ------: | --------: | ---------------: |
| C. 셀마다 하던 PostgreSQL 값 검사에서 타입 이름 배열을 새로 만들고 여러 번 비교하는 작업을, 타입 이름별 분류 조회 한 번으로 바꿨습니다 | DB 통신 제외, 10,000행 × 32열               | 11.06ms |  9.01ms |     18.8% |       7회 중 7회 |
| C. 같은 변경                                                                                                                           | 실제 PostgreSQL, 같은 SQL로 10,000행 × 31열 |       - |       - |      4.8% |       7회 중 7회 |
| C. 같은 변경                                                                                                                           | 실제 PostgreSQL, 일반 API로 10,000행 × 31열 |       - |       - |      3.7% |       7회 중 7회 |
| D. 쿼리마다 하던 `RenderedStatement` 검증에서 중복 순회, 불필요한 `Set` 생성, 조건부 spread 복사를 없앴습니다                          | DB 통신 제외, 옵저버 없음, 파라미터 1개     |   3.4µs |   2.9µs |     13.8% |       6회 중 7회 |
| D. 같은 변경                                                                                                                           | DB 통신 제외, 옵저버 없음, 파라미터 10개    |   6.8µs |   5.5µs |     19.1% |       7회 중 7회 |
| D. 같은 변경                                                                                                                           | DB 통신 제외, 옵저버 없음, 파라미터 50개    |  19.2µs |  14.8µs |     22.7% |       7회 중 7회 |

변경 C의 비교 기준은 변경 B까지 적용한 빌드이고, 변경 D의 비교 기준은 변경 C 이전의 HEAD `core`입니다. 두 비교 모두 한 패키지만 교체했습니다.

변경 D를 실제 PostgreSQL의 작은 쿼리에 적용한 결과는 SQLBraid가 2~~4% 빨랐지만 이긴 횟수가 9회 중 5~~7회였습니다. 같은 실험에서 pg 대조군은 ±1.3% 안에 있었습니다. 실제 작은 쿼리의 개선은 확정하지 않습니다.

측정하고도 바꾸지 않은 곳이 있습니다. 템플릿 렉시컬 검증의 캐시 키(`JSON.stringify(profile)`)는 쿼리당 약 1µs입니다. 렉시컬 프로파일이 동결되지 않은 일반 객체여서, 객체 신원으로 캐시하면 프로파일을 바꾼 뒤의 검증을 놓칠 수 있습니다. 이득이 이 위험보다 작다고 판단했습니다.

원시 결과: `results/decode-kind-paired/`, `results/decode-kind-paired-pg/`, `results/core-statement-paired/`, `results/core-statement-paired-pg/`. 모두 로컬 자료이며 Git에서 제외됩니다.

### 다른 어댑터 점검 (1차 측정)

`tests/performance/decode-cost.mjs`는 DB 없이 어댑터별 `TypePolicy.decode`의 셀당 비용을 잽니다(같은 입력을 2,000,000회 반복한 중앙값, 값이 상수라 절대값보다 어댑터 간 비교에 쓰는 수치입니다).

| 어댑터        | 변경 전          | 변경 후   |
| ------------- | ---------------- | --------- |
| PostgreSQL    | 변경 C 전 미측정 | 16~31ns   |
| SQLite        | 13~20ns          | 변경 없음 |
| MySQL·MariaDB | 19~32ns          | 변경 없음 |
| SQL Server    | 26~39ns          | 6~20ns    |
| Oracle        | 100~111ns        | 9~19ns    |

Oracle과 SQL Server는 셀마다 `trim`, 대소문자 변환, 정규식 공백 정리를 다시 했습니다. 이미 정규화된 매핑 이름은 바로 쓰고 그 밖의 이름은 기존 방식으로 처리합니다. 임의의 이름을 저장하는 캐시는 추가하지 않았습니다. 동등성은 `tests/type-name-normalization.test.ts`가 확인하며, 변경 전 코드에서도 통과합니다.

`tests/performance/sqlite.mjs`는 메모리 SQLite에서 드라이버 직접 호출과 SQLBraid를 비교합니다(7회, 순서 교대, 값은 회차별 중앙값). 기준선은 호출마다 `prepare`하고 int64를 BigInt로 읽는 직접 호출입니다. SQLBraid도 같은 일을 하기 때문입니다.

| 드라이버       | 조회     | 직접 호출 | SQLBraid | 비율 |
| -------------- | -------- | --------: | -------: | ---: |
| node:sqlite    | 1행      |     5.0µs |   14.7µs | 2.94 |
| node:sqlite    | 100행    |    60.4µs |   76.3µs | 1.26 |
| node:sqlite    | 10,000행 |   5,652µs |  6,092µs | 1.08 |
| better-sqlite3 | 1행      |     6.4µs |   18.9µs | 2.94 |
| better-sqlite3 | 100행    |    42.0µs |   65.3µs | 1.55 |
| better-sqlite3 | 10,000행 |   3,590µs |  4,536µs | 1.26 |

이 비교의 직접 호출은 배열 행을 돌려주고 SQLBraid는 객체 행과 검사를 포함하므로 비율의 일부는 필요한 일입니다. 1행 조회의 차이 약 10µs 중 `columns()` 네이티브 호출이 2.8~4.7µs이고, 나머지는 PostgreSQL에서 본 공통 JS 경로(템플릿 검증, 문장 생성, 바인딩 설명)입니다. SQLite 전용 낭비는 확인하지 못했습니다. `better-sqlite3`의 대량 조회 차이 중 `safeIntegers(true)`에 의한 BigInt 전송 비용은 정확한 정수를 문자열로 주는 설계에서 오며 줄이지 않았습니다.

`tests/performance/mysql.mjs`는 전용 MySQL 8.4.2 컨테이너에서 mysql2 직접 호출과 SQLBraid(`MYSQL2_NATIVE` 연결 옵션, 연결 1개)를 비교합니다(7회, 순서 교대, 회차별 중앙값). `execute`는 객체 행을 받는 prepared 호출입니다. `noEvalArray`와 `noEvalObjects`는 SQLBraid 어댑터와 같은 `disableEval: true` 파서를 쓰는 기준선입니다. `noEvalObjects`는 배열 행을 같은 키의 객체로만 바꿉니다.

| 조회     | execute | noEvalArray | noEvalObjects | SQLBraid | SQLBraid/execute |
| -------- | ------: | ----------: | ------------: | -------: | ---------------: |
| 1행      |  87.4µs |      90.1µs |        89.8µs |  124.2µs |             1.42 |
| 100행    | 162.6µs |     178.9µs |       188.2µs |  223.3µs |             1.37 |
| 10,000행 | 3,852µs |     4,604µs |       6,447µs |  8,792µs |             2.28 |

- 10,000행에서 SQLBraid가 `noEvalArray` 위에 더하는 약 4.2ms 중 약 1.8ms는 `sql.rows`의 객체 행 생성입니다. 나머지 약 2.3ms(셀당 약 23ns)는 숫자 검사, `TypePolicy.decode`, 정확한 정수를 문자열로 바꾸는 일입니다. 프로파일에서 특정 한 곳이 아니라 여러 곳에 나뉘어 있었습니다.
- `execute`와의 차이에는 mysql2의 `disableEval: true` 파서 차이(약 0.8ms)도 들어 있습니다.
- 1행의 고정 비용은 약 15µs입니다. `tests/performance/mysql-layers.mjs`가 직접 호출, 어댑터 실행기, `db.all`을 같은 회차에서 번갈아 11회 잰 값이며, 같은 회차 안의 차이(`db.all` − 직접 호출)의 중앙값입니다. 벽시계 시간으로 약 16µs(어댑터 실행기까지 약 5µs), CPU 시간으로 약 12µs(어댑터 실행기까지 약 7µs)입니다. 직접 호출 자체가 회차마다 84~106µs로 흔들려서, 변형별로 따로 잰 값의 차이(`mysql.mjs`의 약 35µs)는 이 흔들림이 섞여 과대하게 나옵니다. 서버 왕복 횟수(`Com_stmt_execute` 100회에 100회)와 `connection.execute`에 넘기는 인자는 같습니다.
- 이 고정 비용에 두드러지는 한 곳은 없습니다. 1행 조회의 CPU 프로파일에서 `@sqlbraid` 프레임은 호출당 합계 4.7µs이고, 가장 큰 함수도 0.42µs입니다(`createQuery`, `validateNativeTemplate`). 그다음은 `assertUniqueFields` 0.33µs, `createStatementBindingDescription` 0.29µs, `prepareMysqlRowProjector` 0.27µs, `assertBindingDescription` 0.25µs입니다. DB 없는 실행기로 잰 템플릿 생성·렌더·런타임 전체는 2.7µs입니다. CPU 차이 12µs 중 프로파일의 함수 시간으로 설명되는 몫은 약 5µs이고, 나머지는 할당과 GC 등 여러 곳에 퍼져 있어 함수 단위로 분리하지 못했습니다. 그래서 이 부분은 코드를 바꾸지 않았습니다.
- mysql2의 `trace` 옵션(`Error.captureStackTrace`)을 끄고 같은 회차에서 13회 번갈아 다시 쟀습니다. 직접 호출은 벽시계 87.9µs → 83.2µs, CPU 23.6µs → 19.1µs로 줄었고, `db.all`은 벽시계 102.6µs → 92.7µs, CPU 38.1µs → 32.4µs로 줄었습니다. 그래서 스택 깊이 차이로 설명되는 몫은 최대 1~5µs입니다. `trace`는 사용자가 정하는 연결 옵션이고 SQLBraid가 바꾸지 않습니다. 프레임 수를 줄이려면 async 단계를 합쳐야 하는데, 얻는 몫이 이 크기이고 오류 전달과 마이크로태스크 순서를 건드려서 하지 않았습니다.
- MySQL 셀 변환을 열마다 한 번만 고르도록 바꿨습니다(`packages/mysql/src/type-policy.ts`의 `resolveCellDecoder`와 `mysql2.ts`의 `prepareMysqlRowProjector`). 이전에는 셀마다 숫자 검사 클로저를 부르고 `policy.decode`에서 `trim().toUpperCase()`와 타입 비교 사슬을 다시 실행했습니다. 지금은 열을 준비할 때 타입별 함수를 한 번 고릅니다. 이 선택은 SQLBraid가 만든 정책에만 적용되고, 사용자가 넘긴 정책은 기존 `policy.decode` 경로를 그대로 씁니다. 공개 `TypePolicy`에는 멤버를 추가하지 않았고, `policy.decode` 자체는 같은 타입별 함수를 쓰는 하나의 구현입니다.
  - **동등성:** 기준 빌드와 변경 빌드에 같은 가짜 mysql2 연결을 주고 프로파일 4개 × 타입 28개 × 값 24개 = 2,688건을 비교했습니다. 결과와 오류 클래스·메시지가 모두 같았습니다(오류 1,220건 포함, 불일치 0건). 저장소에는 `tests/type-name-normalization.test.ts`의 MySQL 항목을 추가했습니다.
  - **DB 없는 실행기, 10,000행 × 10열:** 2.97ms → 1.56ms. 15회 모두 변경 빌드가 빨랐습니다(`tests/performance/mysql-cell-free.mjs`).
  - **실DB, 같은 프로세스에서 두 빌드를 9회 번갈아 측정:** 1행은 124.7µs → 124.5µs(변화 없음), 100행은 228.5µs → 213.6µs(약 15µs, 9/9회), 10,000행은 8,924µs → 7,686µs(약 1,230µs, 14%, 9/9회)입니다(`tests/performance/mysql-compare-builds.mjs`). 1행 조회에는 효과가 없습니다.
  - **정정:** 이 문서의 이전 판은 타입명 정규화만 줄인 실험이 "효과 없음"이라고 적었습니다. 그 실험의 빌드 명령(`pnpm --filter @sqlbraid/mysql build`)은 이 저장소에 없는 스크립트라서 변경이 반영되지 않은 빌드로 쟀습니다. 따라서 그 결론은 근거가 없어서 삭제했습니다. 빌드는 저장소 루트의 `pnpm exec tsdown`으로 하며, 빌드 후 `dist`에 변경이 들어갔는지 확인해야 합니다.
  - **다른 어댑터:** 아래 표를 보세요.

`packages/mssql`, `packages/mariadb`, `packages/oracle`, `packages/postgres`에도 같은 방식을 적용했습니다. 모든 어댑터에서 SQLBraid가 만든 정책일 때만 열마다 한 번 고르고, 사용자 정책은 기존 `policy.decode` 경로를 씁니다. `policy.decode` 자체도 같은 타입별 함수를 쓰는 하나의 구현이며, 오류 메시지는 호출자가 쓴 타입 이름을 그대로 담습니다. SQLite 계열(node:sqlite, better-sqlite3, libSQL, D1, WASM)은 `policy.decode`를 쓰지 않고 셀당 `typeof` 검사 하나만 하므로 바꾸지 않았습니다.

| 어댑터     | 동등성 비교(기준 빌드와 결과·오류 메시지) | DB 없는 실행기, 10,000행 × 10열 | 실DB, 10,000행 (짝 차이, 9회 중 빠른 횟수) |
| ---------- | ----------------------------------------- | ------------------------------- | ------------------------------------------ |
| MySQL      | 2,688건, 불일치 0                         | 2.97ms → 1.56ms                 | 8,924µs → 7,686µs (−14%, 9/9)              |
| MariaDB    | 2,496건, 불일치 0                         | 3.04ms → 1.57ms                 | 6,607µs → 5,115µs (−23%, 9/9)              |
| PostgreSQL | 3,168건, 불일치 0                         | 2.82ms → 1.40ms                 | 11,268µs → 9,633µs (−15%, 9/9)             |
| Oracle     | 525건, 불일치 0                           | 1.91ms → 1.20ms                 | 29,879µs → 28,804µs (−3.7%, 9/9)           |
| SQL Server | 1,254건, 불일치 0                         | 2.93ms → 1.72ms                 | 12,000µs → 10,213µs (−14.9%, 9/9)          |

- DB 없는 실행기는 가짜 연결이 고정된 행을 돌려주고, 두 빌드를 15회 번갈아 쟀습니다. 모든 어댑터에서 15회 모두 변경 빌드가 빨랐습니다(`tests/performance/*-cell-free.mjs`).
- 실DB는 같은 프로세스에서 두 빌드를 번갈아 쟀습니다(`tests/performance/*-compare-builds.mjs`). 1행과 100행은 어댑터마다 0~15µs 정도이고 일부 회차에서는 변경 빌드가 느렸습니다. 작은 조회에서 효과는 확정하지 못했습니다.
- PostgreSQL 실DB 조회는 `generate_series`로 만든 10열 결과입니다. 다른 어댑터는 `perf_t` 테이블을 읽습니다.
- 저장소 DB 테스트가 통과했습니다: MySQL 65개, MariaDB 58개, PostgreSQL 144개, Oracle 68개, SQL Server 53개. 단위·CLI 테스트는 1,298개입니다.

SQL Server 실DB 비교는 에뮬레이션 서버에서 두 빌드를 같은 프로세스에서 번갈아 쟀습니다(`tests/performance/mssql-compare-builds.mjs`). 서버가 느려서 절대값은 다른 DB와 비교하지 않습니다. 1행(217.2µs → 214.6µs)과 100행(351.5µs → 347.4µs)은 잡음 수준입니다. 이 앞서 넣은 Oracle·SQL Server 타입명 정규화 변경만의 실DB 효과는 변경 전 빌드가 없어 분리하지 못했습니다.

### SQLite 계열(libSQL, WASM, D1)과 Bun.SQL

`tests/performance/sqlite-family.mjs`는 메모리 데이터베이스에서 드라이버 직접 호출과 SQLBraid를 비교합니다(7회, 순서 교대, 회차별 중앙값, D1은 5회). 기준선에는 객체 행으로 바꾸는 변형을 함께 두었습니다. D1은 Miniflare 바인딩을 쓰므로 호출마다 약 9ms의 RPC 비용이 있고, 절대값은 실제 D1과 다릅니다.

| 드라이버 | 조회     | 직접 호출 (객체 행) | SQLBraid | 비율 |
| -------- | -------- | ------------------: | -------: | ---: |
| libSQL   | 1행      |              25.2µs |   32.5µs | 1.29 |
| libSQL   | 100행    |             329.4µs |  341.9µs | 1.04 |
| libSQL   | 10,000행 |            31,530µs | 31,838µs | 1.01 |
| WASM     | 1행      |              14.4µs |   24.1µs | 1.68 |
| WASM     | 100행    |             459.5µs |  479.1µs | 1.04 |
| WASM     | 10,000행 |            46,800µs | 47,005µs | 1.00 |
| D1       | 1행      |             9,067µs |  9,583µs | 1.06 |
| D1       | 100행    |             9,711µs | 10,056µs | 1.04 |
| D1       | 10,000행 |            60,936µs | 47,499µs | 0.78 |

세 어댑터 모두 100행 이상에서 직접 호출과 거의 같고, 1행의 고정 비용은 libSQL 약 7µs, WASM 약 10µs입니다. D1의 10,000행에서 SQLBraid가 빠른 것은 `all()`이 객체 행을 만드는 비용이 더 크기 때문으로 보이며, 원인을 분리하지는 않았습니다.

`tests/performance/bun-sql.mjs`는 Bun 1.3.14에서 `client.unsafe()` 직접 호출과 SQLBraid를 비교합니다. 변경 전 Bun.SQL SQLite 10,000행은 직접 호출 2.19ms, SQLBraid 9.72ms(4.4배)였습니다. 다른 어댑터(셀당 약 20ns)보다 큰 격차여서 코드를 읽었고, `packages/bun-sql/src/index.ts`의 `normalizeRow`가 셀마다 `Object.defineProperty`로 속성을 정의하는 것을 확인했습니다. 일반 대입으로 바꾸고 `__proto__` 키만 기존 정의 방식을 쓰게 했습니다. 행은 계속 `Object.freeze`합니다.

- **마이크로 측정:** 10,000행 × 10열 행 변환이 Bun에서 5.49ms → 1.89ms, Node에서 10.47ms → 2.22ms였습니다.
- **동등성:** 기준 빌드와 변경 빌드를 실제 Bun.SQL SQLite로 7개 쿼리에서 비교했습니다. 속성 설명자(`writable`, `configurable`), 동결 상태, `__proto__`·`constructor` 열, 오류가 모두 같았습니다. 저장소에는 `tests/rc-bun-sql.test.ts`에 같은 동작 검사를 추가했습니다. 이 검사는 변경 전 코드에서도 통과합니다.
- **실DB, 기준 빌드와 변경 빌드를 9회 번갈아 측정(`tests/performance/bun-sql-compare-builds.mjs`):** SQLite 10,000행 9,611µs → 5,932µs(−38%, 9/9회), 100행 100.1µs → 63.9µs(9/9회), 1행은 변화 없음. PostgreSQL 10,000행 11,692µs → 8,050µs(−31%, 9/9회), 100행 527.5µs → 500.6µs(9/9회). 이 PostgreSQL 측정의 1행(약 430µs)은 한 프로세스에서 Bun.SQL 클라이언트 두 개를 쓴 구성의 지연이라 단독 값으로 읽지 않습니다.
- **남은 격차:** 변경 후 Bun.SQL SQLite는 직접 호출 대비 1행 2.17배, 100행 2.22배, 10,000행 2.74배입니다. 10,000행에서 약 3.8ms 중 행 객체 생성과 BigInt→문자열 변환이 약 1.9ms이고, Bun.SQL은 열 타입 메타데이터가 없어 정확한 정수를 문자열로 바꿔야 하므로 줄이지 않았습니다. 나머지는 여러 곳에 분산되어 더 분석하지 않았습니다.
- **측정 조건:** Bun.SQL은 정수로 보이는 `Number`를 거부하므로(설계된 동작) 벤치마크 테이블의 정수 열은 PostgreSQL에서 `int8`, SQLite에서는 `safeIntegers`로 읽고, 실수 열은 정수가 되지 않는 값입니다.
- **저장소 DB 테스트:** `db-bun-sql` 35개가 통과했습니다.

### UQL 대비 격차

질문은 "UQL보다 SQLBraid가 느린 이유가 tagged template 보간 때문인가"였습니다. 같은 SQL, 같은 값 표현(`equivalent-sql`)으로 `pg`, SQLBraid, UQL을 같은 데이터베이스에서 쟀습니다. 1행과 10행 항목은 11회(새 프로세스), 100행 이상은 5회입니다. 이 구성의 UQL 실행도 같은 tagged template 호출입니다(`tests/performance/postgres.mjs`의 `rawRuns`).

| 항목                     | 직접 `pg` |  SQLBraid |       UQL | SQLBraid − `pg` | UQL − `pg` |
| ------------------------ | --------: | --------: | --------: | --------------: | ---------: |
| 1행, 2열 (11회)          |   100.5µs |   116.2µs |    97.4µs |         +15.7µs |     −3.1µs |
| 1행, 10열 (11회)         |   101.8µs |   119.0µs |   112.3µs |         +17.2µs |    +10.6µs |
| 10행, 10열 혼합 (11회)   |   128.2µs |   141.3µs |   138.9µs |         +13.1µs |    +10.7µs |
| 100행, 10열 혼합 (5회)   |   253.6µs |   301.6µs |   288.0µs |         +48.0µs |    +34.4µs |
| 1,000행, 10열 혼합 (5회) | 1,352.6µs | 1,371.0µs | 1,441.9µs |         +18.4µs |    +89.3µs |

- **측정 잡음:** 라운드 간 표준편차가 직접 `pg`에서 7~~9%, SQLBraid 4~~10%, UQL 6~~11%(약 100µs 기준 4~~11µs)입니다. 따라서 SQLBraid와 UQL의 1행 차이(+18.8, +6.6, +2.4µs)는 개별로는 잡음 안에 있습니다. 같은 구성의 다른 측정에서는 UQL이 직접 `pg`보다 빠르게 나온 적도 있습니다.
- **SQLBraid의 고정 비용:** 1행·10행 세 항목 모두 직접 `pg`보다 13~17µs 느립니다. MySQL 짝 비교의 약 15µs와 같은 크기이고, 이 값이 일관된 부분입니다.
- **tagged template 보간의 몫:** DB 없는 측정에서 태그 생성 0.63µs, 렌더링 0.75µs로 합쳐 약 1.4µs입니다. 이 약 15µs의 약 10%이며, UQL도 같은 태그를 쓰므로 격차의 원인이라고 할 근거가 없습니다. 나머지는 MySQL 프로파일에서 본 것처럼 템플릿 검증, 문장 생성, 바인딩 설명, 런타임, 어댑터 실행기에 고르게 분산되어 있습니다.
- **행이 많은 쪽:** 옵저버·타입명 변경만 적용한 최종 측정(셀 변환 변경 전)에서는 SQLBraid가 UQL보다 9~16% 느렸습니다(1,000행 10열 혼합에서 1,611µs 대 1,385µs). 변경 후 측정에서는 1,000행에서 SQLBraid가 UQL보다 빠릅니다(1,371µs 대 1,442µs). UQL은 `res.rows`를 거의 그대로 돌려주고 SQLBraid는 열마다 변환하기 때문에 행이 많을수록 차이가 컸던 것으로 보이며, 변환 변경으로 대부분 사라졌습니다. 100행에서는 SQLBraid가 UQL보다 13.6µs 느려, 사라졌다고 할 수는 없습니다.
- **결론:** 1행 쿼리에서 SQLBraid는 UQL보다 평균 몇 µs(대략 2~19µs, 개별 값은 잡음 안) 느릴 수 있고, 그 원인을 tagged template 보간으로 돌릴 근거는 없습니다. 이 차이를 완전히 설명하는 한 곳은 찾지 못했습니다.

## 4. 왜 이 두 곳을 바꿨나요?

소스만 보고 추측한 뒤 수정하지 않았습니다. 먼저 실행 시간과 CPU 사용 위치, 메모리 할당을 측정했습니다.

- 옵저버가 없는 실행에서도 `queryReadyEvent`와 관련 배열을 만드는 메모리 할당이 나타났습니다.
- 1,000행의 넓은 결과를 처리하는 CPU 프로파일에서 타입명을 정리하는 `canonical` 함수가 표본 시간의 **26.50%**를 차지했습니다.
- 기존 `perf/row-materialization` 계열 변경은 이미 기준 커밋에 병합되어 있었습니다. 배열 형태로 행을 받고 열별 처리 함수를 준비하는 최적화를 다시 추가하지 않았습니다.

별도로 측정한 호출당 메모리 할당 추정치는 다음과 같습니다. 단위는 바이트이며 반올림한 값입니다.

| 측정 대상                                     |   변경 전 | 해당 변경 후 |
| --------------------------------------------- | --------: | -----------: |
| 옵저버 없음, 파라미터 1개                     |    16,749 |       13,189 |
| 옵저버 없음, 파라미터 50개                    |    80,803 |       66,340 |
| DB 통신 제외, pg 어댑터의 1,000행 × 32열 처리 | 3,148,059 |      557,156 |

이 표는 실행 중 만들었다가 버린 객체까지 포함한 **할당량 추정치**입니다. 실행이 끝난 뒤 메모리에 남아 있는 크기와 다릅니다. 각 조건에서 한 번씩 프로파일링한 결과이며, 측정 도구 자체의 비용도 포함합니다. 메모리 할당이 줄어든 비율만큼 응답 시간도 줄어든다는 뜻은 아닙니다.

단계별로 보면 비용은 두 종류였습니다.

- **쿼리마다 드는 비용:** 템플릿 처리, 파라미터 바인딩, 실행 순서 관리, 옵저버 이벤트 준비입니다. 작은 결과에서는 이 비용의 비중이 큽니다.
- **행·열 수에 따라 늘어나는 비용:** 행 객체 생성, 값 표현 검사, 사용자 스키마 검증입니다. 큰 결과에서는 이 비용의 비중이 커집니다.

행 수가 늘면 비용도 대체로 늘었지만, 항상 정확한 비례 관계는 아니었습니다. 작은 결과로 예측한 시간과 10,000행의 실제 시간이 달라서, 하나의 ‘쿼리당 고정 비용’으로 모든 경우를 설명하지 않았습니다.

## 5. 어떻게 측정했나요?

### 실제 DB와 DB 없는 실험을 나눴습니다

| 환경            | 포함하는 작업                                                | 이 결과로 판단할 수 있는 것      |
| --------------- | ------------------------------------------------------------ | -------------------------------- |
| 실제 PostgreSQL | 라이브러리 처리, pg 드라이버, DB 실행, 통신                  | 사용자가 기다리는 전체 시간      |
| DB 없는 실험    | 정해진 결과를 돌려주는 실행기를 통한 템플릿·바인딩·결과 처리 | JavaScript 쪽의 비용과 수정 효과 |

DB 없는 실험은 실제 pg 네트워크 처리나 서버 동작을 재현하지 않습니다. 반대로 실제 DB 응답 시간의 차이만으로 라이브러리 내부의 각 비용을 정확히 분리할 수도 없습니다.

### 한 번 실행한 결과로 판단하지 않았습니다

- 최적화 전 전체 측정은 새 프로세스 **5회**, 최종 전체 측정은 **3회** 실행했습니다.
- 각 최적화는 기존 빌드와 변경 빌드를 **7쌍**으로 비교했습니다. 기존 빌드를 먼저 실행했다면 다음 쌍에서는 변경 빌드를 먼저 실행했습니다.
- 각 회차에서 측정 항목의 순서를 섞고, 준비 실행을 한 뒤 시간을 쟀습니다.
- 연결 생성, 테스트 데이터 준비, 결과가 맞는지 확인하는 작업은 일반 쿼리 측정에서 제외했습니다. 초기 연결 비용은 별도 항목입니다.
- 일반 측정 중에 강제로 GC를 실행하지 않았습니다. CPU·메모리 프로파일링은 별도 실행했습니다.

DB 없는 실험은 461개, PostgreSQL 실험은 292개입니다. 기준 측정에는 총 9,639,873개의 호출 시간 표본을 저장했습니다. Bun에서는 317개 항목의 축소 실험을 3회 실행했습니다.

측정 범위에는 단건·다건 조회, 1·10·50개 파라미터, 동적 SQL, 준비된 쿼리, 풀·세션·트랜잭션, 스키마 변환, 스트리밍, 쓰기가 포함됩니다.

### 통계 용어는 이렇게 읽으면 됩니다

| 용어                   | 뜻                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| 중앙값                 | 작은 값부터 정렬했을 때 가운데 값입니다. 일부 매우 느린 실행의 영향을 평균보다 덜 받습니다. |

이 보고서의 P50·P95는 각 회차에서 구한 값을 다시 중앙값으로 요약했습니다. 모든 회차의 호출을 하나로 합쳐 계산한 값은 아닙니다.

## 6. 비교할 때 주의할 조건

### 라이브러리마다 기본 반환값이 다릅니다

숫자와 날짜의 반환 형태가 다르면 속도만 비교할 수 없습니다. 이 실험은 결과값이 같은지 먼저 검사하고, 필요한 조건을 기록했습니다.

- SQLBraid는 `pg-native` 프로파일에서도 정확한 정수를 문자열로 유지합니다. 비교용 조회에서는 int4 열을 `float8`로 명시적으로 변환했습니다. int4 범위의 정수는 이 변환으로 정밀도를 잃지 않습니다.
- 같은 SQL 비교에서는 모든 라이브러리에 같은 변환을 적용했습니다. 날짜·시각도 SQL에서 텍스트로 변환해 Drizzle의 파서 차이를 피했습니다.
- UQL에는 `pg.types`를 명시적으로 전달했습니다. 따라서 UQL의 기본 타입 파서 설정 그대로 측정한 결과는 아닙니다. 정확한 숫자를 다루는 엔티티 필드도 문자열로 선언했습니다.
- SQLBraid의 기본 무손실 표현은 별도 항목으로 측정했습니다. 라이브러리의 기본 정책 자체를 더 빠른 표현으로 바꾸지 않았습니다.
- JavaScript `Date`를 쓰는 비교와 마이크로초 단위 시각을 텍스트로 보존하는 비교는 분리했습니다.

이 조건 때문에 ‘그냥 설치해서 기본 설정으로 사용했을 때의 순위’로 읽으면 안 됩니다.

### 동시 처리량은 서비스 전체의 처리량이 아닙니다

풀 크기를 4로 고정하고, 한 번에 독립적인 SELECT 4개를 실행했습니다. 아래 P50·P95는 **네 쿼리가 모두 끝날 때까지의 시간**입니다. 단위는 µs입니다.

| 구현     | 4개 완료 시간 P50 | 4개 완료 시간 P95 | 초당 완료 쿼리 수 |
| -------- | ----------------: | ----------------: | ----------------: |
| pg       |            175.75 |            216.79 |            22,536 |
| SQLBraid |            195.88 |            230.13 |            20,172 |
| UQL      |            165.83 |            214.25 |            23,648 |
| Kysely   |            164.58 |            210.00 |            23,587 |
| Drizzle  |            173.83 |            216.96 |            22,389 |

처리량은 묶음당 평균 시간을 기준으로 환산했습니다. 실제 서비스의 최대 처리량이나 개별 요청의 대기 시간을 검증한 수치는 아닙니다.

### 나머지 한계

- 쓰기 실험은 데이터가 계속 늘지 않도록 변경을 되돌리는 SQL도 함께 실행합니다. 단건 쓰기는 변경과 복구 2개 명령, 배치 INSERT는 삽입 10개와 복구 DELETE 1개를 함께 측정합니다.
- 자동 커밋과 하나의 트랜잭션으로 묶은 쓰기는 따로 측정했습니다. DB 쓰기 시간을 SQLBraid 내부 비용이라고 부르지 않았습니다.
- CPU 코어, 온도, 전원 상태, 다른 프로세스의 부하는 완전히 고정하지 못했습니다.
- 큰 결과의 일부 항목은 회차당 표본이 16개입니다. 운영 환경의 느린 응답을 분석하려면 더 긴 측정이 필요합니다.
- 다른 라이브러리에 공개 API가 없는 준비된 쿼리·세션·스트리밍 항목은 흉내 내서 채우지 않았습니다.
- 초기화 측정에는 객체 생성, 연결, 첫 쿼리, 종료를 포함했습니다. 모듈 로딩과 UQL 엔티티 등록은 제외했습니다.
- Bun CPU 프로파일에는 프로그램 시작과 실험 준비도 포함됩니다. Node의 준비 완료 후 프로파일과 같은 조건으로 비교하지 않았습니다.
- 다른 DB 어댑터는 동작을 검증했습니다. PostgreSQL에서 측정한 개선율을 MySQL·Oracle 등에도 적용할 수는 없습니다.

전체 측정에서 일부 값이 더 느려 보이는 경우도 있었습니다. 변경하지 않은 컴파일된 템플릿과 자동 커밋 DELETE를 7쌍으로 추가 비교했지만, 이번 변경이 원인인 성능 악화는 확인하지 못했습니다. 이것이 모든 조건에서 성능이 완전히 같다는 증명은 아닙니다.

로컬 검증을 통과한 상태이며, 새 커밋에 대한 CI 인증이나 릴리스 완료를 의미하지 않습니다. 커밋·태그·배포는 수행하지 않았습니다.

## 8. 적용하지 않은 최적화와 측정 과정의 수정

다음 변경은 적용하지 않았습니다.

- **템플릿 캐시 추가:** 템플릿 객체의 동일성을 이용하는 캐시가 이미 있습니다. 임의 SQL 문자열을 계속 쌓는 캐시는 추가하지 않았습니다.
- **행 객체 처리 구조 재설계:** 과거 행 처리 최적화는 이미 병합되어 있습니다. 런타임 코드 생성이나 새 결과 형식을 추가하지 않았습니다.
- **스키마 검증의 `await` 제거:** 사용자 검증 함수는 비동기로 동작하거나 DB를 다시 호출할 수 있습니다. 별도 동작 검증 없이 바꾸지 않았습니다.
- **열별 디코더 인터페이스 추가:** 이번에는 기존 타입명 확인만으로 측정 가능한 개선이 나왔습니다.
- **컴파일 경로 변경:** 값 계산이 저렴한 실험에서는 컴파일 경로가 항상 더 빠르지 않았습니다. 실행하지 않는 분기의 식을 평가하지 않는 이점과 렌더링 속도는 구분했습니다.

프로덕션 코드에 적용한 두 변경은 모두 유지했습니다. 측정 도구에서는 다음 문제를 수정했습니다.

- 처음에는 매우 짧은 작업의 표본이 지나치게 많이 쌓여 JSON 생성 한도를 넘었습니다. 그 실행은 폐기하고, 정식 기준 측정부터 호출 수를 16~8,192개로 제한했습니다.
- Tinybench 6.1.4에는 P95 필드가 없어 최초 요약에서 빠졌습니다. 저장한 호출 시간을 바꾸지 않고 P95를 계산해 요약을 다시 만들었습니다.
- 테스트용 코드의 예약어 함수명, 빈 SET, 잘못된 명령 결과 접근도 기준 측정 전에 고쳤습니다. SQLBraid 제품 코드의 결함이나 최적화 성과로 집계하지 않았습니다.

PostgreSQL 이미지는 `postgres:17.6`이며, 사용한 이미지 식별자는 `sha256:00bc86618629af00d2937fdc5a5d63db3ff8450acf52f0636ec813c7f4902929`입니다. 벤치마크는 전용 `sqlbraid_perf` DB만 사용합니다. 이식성 검사는 별도의 지정 버전 DB를 사용했습니다.

## 10. 파일 정리와 다시 실행하는 방법

| 파일·디렉터리                                     | Git 포함 여부      | 용도                                                          |
| ------------------------------------------------- | ------------------ | ------------------------------------------------------------- |
| `tests/performance/`의 코드·SQL·설정·실행 안내    | 포함               | 실험을 다시 실행하는 데 필요합니다.                           |
| `docs/performance/*.md`                           | 포함               | 결론, 방법, 해석, 근거 요약을 남깁니다.                       |
| `docs/performance/results/`                       | 제외               | 원시 측정값, JSON 요약, CPU·메모리 프로파일, 실행 로그입니다. |
| `tests/performance/.builds/`, `.micro-fixture-*/` | 기존 규칙으로 제외 | 비교용 로컬 빌드와 임시 컴파일 파일입니다.                    |

**Git 제외는 로컬 파일 삭제가 아닙니다.** 기존 측정 자료는 그대로 남아 있습니다. 새로 저장소를 복제하면 원시 결과는 없으므로 다시 실행하거나 별도 첨부로 받아야 합니다.

현재 숫자의 근거가 되는 로컬 경로는 다음과 같습니다. 모두 `docs/performance/results/` 아래에 있습니다.

- `baseline/`: 최적화 전 전체 측정입니다.
- `final/`: 최적화 후 전체 측정입니다. 2절의 라이브러리 비교는 `postgres-summary.json`에서 계산했습니다.
- `observer-paired/`, `canonical-paired/`: 3절의 변경별 7쌍 비교입니다.
- `negative-controls/`: 느려 보였던 항목의 추가 비교입니다.
- `profiles/`: CPU·메모리 프로파일입니다. 메모리 프로파일은 `.heapprofile.gz`로 압축했습니다.
- `verification/`: 이전 검증의 로그와 `gates.json`입니다.

빌드와 전용 DB 준비는 [실행 안내](../../tests/performance/README.md)를 따르세요. 준비 후 저장소 루트에서 실행합니다.

```sh
pnpm benchmark:performance --suite micro --rounds 5 --time 100 --warmup 100 \
  --out docs/performance/results/local-micro
pnpm benchmark:performance --suite postgres --rounds 5 --time 100 --warmup 100 \
  --out docs/performance/results/local-postgres
```

`--time`은 항목당 목표 측정 시간입니다. 실제 호출 수는 제한되므로 정확히 그 시간 동안 실행한다는 뜻은 아닙니다. 이 보고서의 원래 기준 측정은 DB 없는 실험에 목표 25ms, PostgreSQL에 100ms, 준비 실행에 각각 50ms를 사용했습니다.

상세 계산과 소스 이력은 [기준 측정 상세 자료](2.0.0-baseline.md)와 [실행 과정·과거 최적화 조사](2.0.0-execution-pipeline.md)에 영문으로 보존했습니다. 원시 결과를 공유할 때는 Git에 넣는 대신 `results/`를 별도 파일로 첨부하면 됩니다.

다음 단계에서는 조용한 장비에서 실제 PostgreSQL 측정을 더 길게 반복하는 것이 우선입니다. 이번 결과만으로 릴리스 성능 기준이나 모든 서비스에 적용되는 개선율을 정하지 않습니다.
