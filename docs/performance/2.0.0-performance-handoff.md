# SQLBraid 성능 작업 인계

작성일: 2026-10-19. 갱신: 같은 날, 어댑터 변경을 커밋하고 `main`에 병합한 뒤. 다음 에이전트가 현재 작업을 독립적으로 검토하고 이어가기 위한 문서입니다. 기존 보고서를 검증 완료된 결론으로 취급하지 마세요.

## 1. 사용자 요청과 남은 질문

처음 요청은 SQLBraid 2.0.0의 재현 가능한 성능 측정과 실제 코드 최적화였습니다. PostgreSQL/pg를 주 대상으로 하되, 네트워크 없는 실험으로 비용을 분리하고 다른 어댑터의 동작도 유지해야 합니다.

현재 대화에서 남은 질문은 다음과 같습니다.

> 선언형 쿼리 빌더에 가까운 UQL보다 SQLBraid가 느린 이유는 무엇인가? Tagged template 보간 때문인가?

이 질문에 대해 **UQL과 SQLBraid를 같은 조건으로 단계별 대조한 측정은 아직 없습니다.** 앞선 답변은 소스 차이와 SQLBraid 쪽 측정을 근거로 원인을 추정한 수준입니다.

사용자는 이어서 다음 기준을 명시했습니다.

> 추가 오버헤드가 전체 시간에서 큰 비중을 차지하지는 않으며, pg만으로 모든 최적화를 끝냈다고 확정해서는 안 된다.

사용자는 기존 보고서의 문체와 현재 모델의 판단을 신뢰하기 어렵다고 했고, 다른 에이전트로 인계를 요청했습니다. 한국어로 짧고 구체적으로 설명하세요. 필요한 기능의 비용이라는 이유만으로 현재 구현의 낭비를 정당화하지 마세요. 반대로 작은 차이를 과장하거나 pg 결과를 다른 어댑터에 일반화하지 마세요.

이번 인계 작성에서는 코드나 벤치마크를 추가로 변경하지 않았습니다. 다른 에이전트를 실제로 실행한 상태도 아닙니다.

### 아직 답하지 못한 UQL 비교

확인한 소스 차이는 다음과 같습니다.

- 같은 SQL 비교에서 양쪽 모두 tagged template을 사용합니다. `tests/performance/postgres.mjs`의 `rawRuns`를 보세요.
- 설치된 UQL의 `tests/node_modules/uql-orm/dist/postgres/pgQuerier.js`에서 `internalAll`은 `res.rows`를 반환합니다. 이것만으로 상위 `all()`, 빌더, 엔티티 변환 전체 비용이 없다고 말할 수는 없습니다.
- SQLBraid의 `packages/postgres/src/common/results.ts`는 열별 처리 함수를 준비하고 행·셀을 순회하며 TypePolicy를 적용합니다.
- `packages/template/src/tag.ts`는 값을 복사·고정하고, 일반 템플릿도 검사합니다. 실행 시 렌더링·바인딩·자원 관리가 이어집니다.

**[추정] 고정 실행 비용과 행 변환 비용의 차이가 UQL 대비 차이에 기여할 수 있습니다.** 아직 각각의 기여율을 측정하지 않았습니다. ‘tagged template 때문’, ‘안전성 때문에 불가피’, ‘행 변환이 전부’라는 결론은 근거가 부족합니다.

## 5. 측정 결과를 읽을 때 주의할 점

- `logical`은 자연스러운 API로 같은 값을 얻는 비교이고, `equivalent-sql`은 같은 SQL을 직접 실행하는 비교입니다. 둘을 한 순위로 합치지 마세요.
- UQL에는 기본 파서 대신 `pg.types`를 전달했습니다. 정확한 숫자를 다루는 엔티티 필드도 문자열로 선언했습니다.
- SQLBraid의 `pg-native`도 정확한 정수는 문자열입니다. 비교용 SQL은 int4를 `float8`로 변환합니다. 같은 SQL 비교에서는 모든 구현에 같은 변환을 적용합니다.
- Drizzle의 날짜 파서 차이 때문에 같은 SQL 비교는 날짜·시각을 텍스트로 변환합니다. 기본 무손실 표현은 별도 항목입니다.
- 쓰기 측정에는 데이터를 복구하는 SQL도 포함됩니다. 단건 변경 1개의 지연 시간으로 읽으면 안 됩니다.
- `--time`은 목표 시간입니다. 준비 측정으로 호출 수를 16~8,192개로 정합니다. 큰 결과의 일부 항목은 회차당 표본이 16개여서 꼬리 지연 추정이 약합니다.
- 기준 5회와 최종 3회의 평균을 단순히 빼서 변경의 효과라고 말하지 마세요. 변경별 교대 비교를 우선 확인하세요.
- 프로파일링은 일반 측정과 분리했습니다. 할당 표본은 셀당 1회뿐이고 측정 도구의 비용이 포함됩니다. Bun CLI CPU 프로파일에는 시작·준비 비용도 포함됩니다.
- Tinybench의 호출별 표본은 정렬되어 있습니다. 원래 호출 순서나 특정 시점의 GC를 복원할 수 없습니다.
- 이식성·실DB 테스트 통과는 다른 어댑터의 성능 검증이 아닙니다.

이미 수정한 측정 도구 문제도 있습니다. 최초 전체 micro 실행은 표본이 너무 많아 JSON 생성 한도를 넘었고 폐기했습니다. 또한 Tinybench 6.1.4에 P95 필드가 없어 최초 요약에서 누락됐습니다. 현재 코드는 원시 표본의 `ceil(0.95 * N) - 1` 위치로 계산하며, 기존 요약도 원시 시간을 바꾸지 않고 다시 만들었습니다. 이전 리뷰에서 발견되지 않은 문제이므로, 리뷰 결과보다 실제 코드와 데이터를 우선하세요.

## 6. 바로 이어서 확인할 순서

새 최적화를 쌓기 전에 아래를 독립적으로 확인하는 것을 권합니다. 이 목록은 아직 수행하지 않은 제안입니다.

1. **실험 코드와 원시 자료를 점검합니다.** 비교 SQL, 값 표현, 드라이버 호출 수, 표본 수, 빌드 해시가 의도한 조건인지 확인합니다.
2. **UQL 차이를 분리합니다.** 같은 쿼리·값·결과를 사용해 템플릿 생성/SQL 생성, 실행 관리, 행 처리 비용을 직접 비교합니다. 기존 SQLBraid micro 결과끼리 뺀 값을 UQL과의 차이로 사용하지 않습니다.
3. **드라이버별로 봅니다.** 공유 런타임 변경은 다른 어댑터에서도 측정해야 합니다. SQLite처럼 동기·저비용 드라이버와 MySQL 같은 다른 비동기 드라이버가 다음 비교 후보입니다. Oracle, SQL Server, MariaDB, Bun.SQL도 측정 전에는 완료로 취급하지 않습니다.
4. **수정은 한 가지씩 합니다.** 동작과 자원 소유권을 유지한 상태에서 기존/변경 빌드를 교대로 측정합니다. 결과가 애매하면 개선으로 발표하지 않습니다.

공개 API, SQL 우선 설계, 파라미터 바인딩, 숫자 정밀도, NULL/undefined, 시각, 스키마, 트랜잭션·세이브포인트, 취소, 스트리밍, 준비된 쿼리, 루틴·OUT 처리를 유지해야 합니다. 벤치마크 편의를 위해 제품 인터페이스를 넓히지 마세요. 저장소 `AGENTS.md`와 드라이버 작성 지침이 우선합니다.

## 7. 실행 환경과 시작 명령

이전 측정 환경은 Apple M4/10코어/16 GiB, macOS 26.5.2 arm64, Node 24.22.0, Bun 1.3.14, TypeScript 5.9.3입니다. 실DB 성능 측정은 PostgreSQL 17.6을 사용했습니다.

`sqlbraid-perf-200`(PostgreSQL 17.6) 컨테이너가 `127.0.0.1:55432`에서 실행 중입니다. 수동 `docker run`으로 시작했으므로 같은 이름으로 다시 만들지 마세요. 전용 테스트 DB이며 사용자·암호·DB 이름은 모두 `sqlbraid_perf`입니다. 다른 DB를 벤치마크 대상으로 사용하지 마세요. MySQL, MariaDB, Oracle, SQL Server 측정에 쓴 컨테이너(`sqlbraid-perf-*`)는 측정 뒤 삭제했습니다. 같은 측정을 하려면 `tests/performance/README.md`의 방식으로 전용 컨테이너를 새로 띄우세요. SQL Server 이미지는 amd64여서 arm64 호스트에서는 에뮬레이션으로 돌므로 절대값을 다른 DB와 비교하지 마세요.

**빌드 주의.** 패키지 빌드는 저장소 루트의 `pnpm exec tsdown`(또는 `pnpm run build:packages`)입니다. `pnpm --filter @sqlbraid/<이름> build`는 이 저장소에 없는 스크립트라서 아무것도 빌드하지 않고 오류도 눈에 띄지 않습니다. 이 때문에 한 번 변경이 반영되지 않은 빌드로 측정해서 "효과 없음"이라는 틀린 결론을 냈습니다. 빌드 뒤에는 `grep`으로 `dist`에 변경이 들어갔는지 확인하세요.

기준 빌드는 `tests/performance/.builds/<이름>-baseline/`에 있습니다(MySQL, MariaDB, PostgreSQL, Oracle, SQL Server). Git에서 제외되어 있어 새 clone에는 없습니다. 다시 만들려면 변경 전 커밋을 체크아웃해 빌드하고 `dist`를 복사하세요.

저장소 루트에서:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm run docs:snippets
node --test tests/performance/harness.test.mjs

export SQLBRAID_PERF_URL='postgres://sqlbraid_perf:sqlbraid_perf@127.0.0.1:55432/sqlbraid_perf'

pnpm benchmark:performance --suite micro --filter '^micro/observer/' \
  --rounds 3 --time 100 --warmup 100 \
  --out docs/performance/results/handoff-micro

pnpm benchmark:performance --suite postgres \
  --filter '^postgres/equivalent-sql/indexed-1-2cols/(pg|SQLBraid|UQL)$' \
  --rounds 3 --time 100 --warmup 100 \
  --out docs/performance/results/handoff-postgres
```

기존 `baseline/`, `final/`, 비교 결과 디렉터리를 새 실행으로 덮어쓰지 마세요. 측정 중에 빌드·테스트·다른 벤치마크를 동시에 실행하지 마세요.

로컬에 보존된 빌드 사본:

- `tests/performance/.builds/baseline/runtime`: 옵저버 변경 전 런타임입니다.
- `tests/performance/.builds/observer-only/postgres`: 타입명 변경 전 PostgreSQL 패키지입니다.

`compare.mjs`는 `--package runtime` 또는 `--package postgres`로 **한 패키지만** 교체합니다. 다른 패키지는 현재 빌드를 사용하므로 전체 원본과 전체 후보의 비교라고 해석하면 안 됩니다.

```sh
node tests/performance/compare.mjs --package runtime \
  --baseline tests/performance/.builds/baseline/runtime \
  --suite micro --filter '^micro/observer/' \
  --rounds 7 --out docs/performance/results/handoff-runtime-paired

node tests/performance/compare.mjs --package postgres \
  --baseline tests/performance/.builds/observer-only/postgres \
  --suite micro --filter '^micro/materialization/wide/1000/pg-executor-prebound$' \
  --rounds 7 --out docs/performance/results/handoff-postgres-paired
```

추가 변경을 평가한다면 현재 빌드의 사본을 별도로 보존해야 합니다. 이전 사본을 덮어쓰지 마세요. CPU·할당 측정은 `benchmark:performance:profile`을 사용하며, 정확히 한 항목만 선택해야 합니다. 상세 사용법은 [벤치마크 README](../../tests/performance/README.md)에 있습니다.
