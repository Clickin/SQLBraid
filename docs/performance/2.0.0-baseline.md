# SQLBraid 2.0.0 performance baseline

This report describes the unoptimized production build at commit `100ff97561c058e54c9edfce067393e8a9a64197`.
It does not report optimization results.
All timings, ratios, sample counts, and fitted coefficients below come from stored baseline JSON.
Python scripts read the summaries and compressed samples to calculate these quantities.
No benchmark, build, test, or formatter ran while preparing this report.

For the Korean explanation and final results, read the [performance report](2.0.0-performance-report.md).
Raw measurements under `results/` are local generated files and are excluded from Git.
Links to those files require the local measurements or a separate copy of the results.

## Method and dispersion

Both suites ran five fresh processes, with seed `2119` plus the round index.
Each process shuffled case order deterministically.
The micro target was 25 ms per case; the PostgreSQL target was 100 ms.
Both used 50 ms of warmup.
Sixteen untimed pilot invocations selected a fixed sample count, bounded between 16 and 8,192.
Tinybench also required at least eight warmup iterations.
These targets are calibration inputs, not guaranteed durations for every case.

Verification, fixture setup, pool establishment, and reference queries occur outside timing.
Timed operations include parameter preparation and SQL generation where the case requires them.
Normal measurements use natural garbage collection, without forced collections or timer-overhead subtraction.
The [harness](../../tests/performance/harness.mjs), [runner](../../tests/performance/run.mjs), and [suite guide](../../tests/performance/README.md) define the method.

“Time” below means the median of the five round means, not a pooled sample mean.
“SD” means the sample standard deviation of those five independent round means.
P50 is the median of the five per-round P50 values.
P95 below uses nearest rank: sorted sample index `ceil(0.95 * count) - 1`, then the median across rounds.
Tinybench 6.1.4 does not expose a `p95` field.
The original summary omitted that field; this analysis reconstructs P95 from the preserved samples without remeasurement.

## Fair comparisons and parser differences

The [PostgreSQL source](../../tests/performance/postgres.mjs) records generated SQL and parameters during verification.
The [fixture](../../tests/performance/fixture.sql) includes NULLs, exact numerics, large integers, JSON, and timestamps with microseconds.
Do not treat equivalent values as proof of identical database or driver work.

### Logical comparisons

Logical reads use each library's natural API.
UQL uses `findMany` with entity metadata; Kysely and Drizzle use their query builders.
SQLBraid uses its SQL template API.
UQL hydration and Drizzle array-row mapping remain measured.

SQLBraid uses the built-in `pg-native` representation profile for these cases.
It still preserves exact integers as text.
Its projection therefore casts int4 columns to float8 to match native JavaScript numbers.
Every int32 value is exactly representable by that cast, but the SQL and wire type differ from the other logical participants.
No custom TypePolicy bypasses SQLBraid normalization.

### Equivalent-SQL comparisons

Equivalent-SQL reads use each library's raw SQL API with the same SQL, parameters, and output representation.
All participants receive the int4-to-float8 casts.
All date and timestamptz columns use explicit text casts.
These cases do not measure ORM entity hydration.

The temporal casts address Drizzle's raw execution parser overrides.
Its versioned [node-postgres session source](https://unpkg.com/drizzle-orm@0.45.4/node-postgres/session.js) is listed in `suiteMetadata.sources`.
Native logical cases return `Date` values with millisecond precision.
Equivalent-text and default-lossless cases preserve six fractional digits and remain separate from native results.

### Published UQL configuration

UQL `0.102.6` is not an assumed pass-through wrapper around pg.
Its [pool source](https://unpkg.com/uql-orm@0.102.6/dist/postgres/pgQuerierPool.js) constructs pg with `types: wireTypes(types)`, then applies caller options.
Its [wire parser source](https://unpkg.com/uql-orm@0.102.6/dist/postgres/pgWireTypes.js) changes int8, zoneless timestamp, date, and related arrays per pool.
It does not install those parsers globally.
The source leaves scalar NUMERIC decoding to field-aware hydration.
Its [hydration source](https://unpkg.com/uql-orm@0.102.6/dist/dialect/hydrateColumn.js) distinguishes numeric, bigint, decimal, date, and JSON representations.

The suite passes `types: pg.types` to UQL, overriding its default wire parsers.
It declares entity `amount` and `big` fields as `String` to retain exact pg-native text.
Logical hydration still runs; overriding wire parsers does not remove the entity layer.
These results describe this explicit configuration, not every default UQL application.

pg, SQLBraid, Kysely, and Drizzle share one pool.
UQL owns a separate pool with the same configuration.
That difference remains a fairness limit, despite matching pool sizes and connection warmup.
Further references appear in `suiteMetadata.sources`, including [pg types](https://node-postgres.com/features/types) and [pg queries](https://node-postgres.com/features/queries).

### Lifecycle and observers

## Approximate fixed and per-row terms

Fit `T(n) = a + b*n` by ordinary least squares, with equal weight per cardinality.
`T` is the median round mean in microseconds; `n` is the number of rows.
`a` is an approximate fixed term; `b` is an approximate per-row term.
Neither coefficient is an isolated internal component cost.

The micro fit uses cardinalities 0, 1, 10, 100, and 1,000.
The 10,000-row measurement is held out to expose extrapolation error.

| Shape and stage                        |  a µs | b µs/row |       R² | Observed at 10,000 µs | Prediction error: observed/predicted − 1 |
| -------------------------------------- | ----: | -------: | -------: | --------------------: | ---------------------------------------: |
| Narrow, prebound executor              | 0.382 | 0.083154 | 0.999987 |               834.305 |                                   +0.29% |
| Narrow, no application schema          | 4.654 | 0.084129 | 0.999901 |               831.818 |                                   −1.67% |
| Narrow, synchronous validation         | 5.058 | 0.177901 | 0.999945 |             1,792.641 |                                   +0.48% |
| Nullable-mixed, prebound executor      | 0.677 | 0.275082 | 0.999993 |             2,778.932 |                                   +1.00% |
| Nullable-mixed, no application schema  | 5.609 | 0.265237 | 0.999929 |             2,707.807 |                                   +1.87% |
| Nullable-mixed, synchronous validation | 5.314 | 0.418137 | 0.999984 |             4,234.424 |                                   +1.14% |
| Wide, prebound executor                | 1.814 | 1.390183 | 0.999995 |            13,873.581 |                                   −0.22% |
| Wide, no application schema            | 6.833 | 1.353526 | 0.999993 |            13,678.024 |                                   +1.00% |

Wide synchronous validation invalidates precise linear extrapolation to 10,000 rows.
Fitting all six cardinalities produces a negative intercept, −19.233 µs, despite R² of 0.999955.
A negative latency is not physical; the high R² hides the model's poor fixed-term interpretation.
GC, allocation, cache behavior, and scheduling can cause nonlinear effects, but these records do not isolate their contributions.

These terms include server, transport, driver, and application work.
Large cardinalities dominate the fit, so its intercept need not match the measured empty result.
Do not subtract fitted slopes or intercepts and label the difference an exact normalization or scheduling cost.

The calculation uses the following equations, without weighting by each case's unequal sample count:

```text
b = sum((n - mean(n)) * (T - mean(T))) / sum((n - mean(n))^2)
a = mean(T) - b * mean(n)
R² = 1 - sum((T - a - b*n)^2) / sum((T - mean(T))^2)
```

## Interpretation limits

The strongest baseline signals are the parameter-count trend, the per-row projection work, and allocation in observer-related paths without an observer.
Logical and equivalent-SQL tables answer different questions and must remain separate.
The micro decomposition shows useful boundaries, but bundled private stages prevent exact component subtraction.
The linear fits summarize these fixtures; they do not predict arbitrary schemas or large-result behavior without further measurement.

This report does not establish an optimization win, a production throughput limit, or a release-readiness decision.
It does not replace semantic tests for cancellation, cleanup, transactions, prepared handles, routines, or other adapters.
The stored raw samples, metadata, and profiles remain the evidence for later comparisons.
