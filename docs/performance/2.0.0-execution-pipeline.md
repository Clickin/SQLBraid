# SQLBraid 2.0 execution pipeline

## Scope and evidence

This report describes the PostgreSQL `pg` path at baseline commit
[`100ff97561c058e54c9edfce067393e8a9a64197`](https://github.com/Clickin/SQLBraid/commit/100ff97561c058e54c9edfce067393e8a9a64197).
The research used source files, Git ancestry, and commit patches. It did not run builds, tests, formatters, or benchmarks.

**No performance result appears in this report.** An allocation in source does not prove a measurable allocation after engine optimization.
An asynchronous function does not prove that its scheduling cost dominates database execution.
The hypotheses below remain **unmeasured** until the performance suite tests them.

Source links use the baseline commit. Later optimization commits must not silently change the meaning of this report.
The main path is an ordinary materialized `database.all` query. Commands share most stages.
Streaming differences appear separately. Routine calls and bulk execution have additional paths and are not interchangeable with ordinary queries.

The cleanup order matters. The runtime releases a materialized result's lease **before application schema mapping**, not before adapter row projection.
Moving release earlier would change resource ownership. Moving it later would retain a pooled connection during application code. [S11]

### What the caches actually cache

- `templateCache` is a `WeakMap` keyed by the template strings object. Its inner key combines the lexical profile and nesting limit.
- `cachedTemplate` serializes that profile before checking the cache. A hit avoids `parseTemplate`, not all work in query creation or rendering.
- A query's `getIr` closure retains its resolved IR. Reusing that query avoids another `cachedTemplate` call through this getter.
- `nativeLexicalCache` caches validation for frozen strings and frozen raw strings. `validateNativeTemplate` still serializes the profile before checking it.
- Plain query creation and `renderPlainTemplate` both call `validateNativeTemplate`. A warm frozen template normally reaches the cache on both calls.
- `synthesizedTemplate` caches reconstructed template strings. It first serializes the variant, cooked segments, raw segments, and parameter shapes into a key.
- `createRenderedStatement` recognizes its own statements through `knownRenderedStatements`. Runtime and adapter calls therefore do not repeatedly copy an already recognized statement.
- `createStatementBindingDescription` memoizes placeholder SQL inside one description. Ordinary runtime preparation creates a new description for each execution.

These are source observations, not evidence that cached operations dominate total time. [S1], [S2], [S3], [S4], [S5], [S7]

### Metadata is not a database catalog query

The normal row path uses `result.fields` from the driver. `pgDatabaseType` reads an explicit type name or maps an OID.
`preparePgRowProjector` prepares decoder closures once per result set. It does not perform an external schema lookup. [S12]

The built-in `makeDecoder` still normalizes the database type name for each non-null value.
Its `canonical` helper calls `trim`, `toLowerCase`, and a prefix replacement.
It then selects numeric, JSON, temporal, or container checks. The profile policy itself is cached by `typePolicyForProfile`. [S16]

This distinction prevents two inaccurate claims: metadata preparation is not per-cell field lookup, and prepared columns do not eliminate per-cell policy dispatch.
The default decoder does not repeatedly parse JSON text with `JSON.parse`.
Native JSON parsing belongs to the selected driver parser behavior, while application schemas may perform their own parsing. [S13], [S16]

The materialized path awaits these boundaries: [S5], [S9], [S10], [S11], [S15]

1. Ready-event notification.
2. Direct queue admission or provider acquisition.
3. Driver execution through the physical context.
4. Release of the lease or queue turn.
5. Result-event notification.
6. Each attached schema for each row.
7. Mapped-event notification.

Additional async wrappers propagate these results. This list identifies profiling locations; it is not a measured microtask count.
`notify` is async even when its empty-observer branch returns immediately.
`validateRow` awaits `standard.validate`, including synchronous schema results. Its caller also awaits `validateRow`. [S8], [S11], [S15]

### Streaming differences

`createPgExecutorFor.stream` creates an array-mode cursor and awaits `readCursor` for each batch.
It checks field-label uniqueness per batch, but initializes `projectRow` only once.
It then yields one projected row at a time. [S17]

`streamOperation` retains the lease while consuming and mapping rows.
Its finalizer calls the driver's iterator `return` before releasing the lease.
The PostgreSQL iterator closes its cursor in `finally`; cancellation may terminate and discard the physical connection.
A streaming optimization must preserve early-break, error, cancellation, and cleanup behavior. [S17], [S18]

## Existing row projector architecture

The core provides two helpers in `packages/core/src/driver.ts`: [S14]

- `prepareResultProjector` accepts a prepared row-reading function for each column.
- `preparePositionalResultProjector` accepts a column index and decoder. It reads the positional cell directly, without another row-reader closure.

Both choose between two object-construction paths:

1. With one row or fewer, use fixed-order assignment into a new object.
2. With at least 32 columns and ten rows or fewer, use the same assignment path.
3. Otherwise, build a shape template, copy it with object spread, and overwrite its existing properties.
4. Without a row-count hint, use the template path.

The assignment path uses `defineResultProperty` for `__proto__`.
The template path defines safe own properties before spreading them.
Both return ordinary objects with `Object.prototype`; they do not use null-prototype objects or generated functions. [S14]

The thresholds are existing heuristics. This investigation did not validate their break-even points on the current Node version or machine.
The source comment explains their intent, but it is not a new benchmark result.

PostgreSQL requests array rows and prepares positional columns from field metadata.
Its fallback for object rows lazily builds a decoder map, iterates `Object.entries`, and defines output properties safely.
This fallback does not repeat the old linear field search for every cell. [S10], [S12]

## Falsifiable optimization hypotheses

All five hypotheses are **unmeasured**. Their order reflects source evidence and experiment clarity, not predicted speedup.
Measure the unchanged baseline first. Keep value semantics and observer behavior identical in any later experiment.

### H1. Avoid constructing events when there are no observers

**Evidence:** `observePrepared` constructs `queryReadyEvent` before `notify` checks the observer count.
`finalizePhysical` and `processRows` also construct result and mapped events before that check. [S5], [S8], [S11]

**Hypothesis:** a no-observer path that avoids these constructions reduces runtime-only cost, especially for small results with many binds.

**Experiment:** compare zero observers, one synchronous no-op observer, and one asynchronous observer.
Use identical queries with 0, 1, 16, and 64 binds against the same non-I/O executor.
Profile allocations and event-construction frames separately from driver execution.

**Reject if:** paired runs show no repeatable improvement outside measurement variation, or event order, event immutability, or error aggregation changes.
Do not remove error propagation merely because no observer is registered.

### H2. Reduce repeated work on warm templates

**Evidence:** lexical-cache hits still serialize the profile.
Plain rendering still copies segments and counts SQL bytes.
Structural rendering builds synthesized-template keys after traversal. [S1], [S2], [S3]

**Hypothesis:** stable lexical keys or reusable value-independent shape work reduce warm tag-plus-render cost.

**Experiment:** separate tag creation, rendering a retained query, and tag-plus-render at one stable callsite.
Compare plain templates, stable directive variants, and alternating variants.
Profile `JSON.stringify`, lexical checks, segment copying, and byte counting.

**Reject if:** gains disappear once warm-cache behavior is isolated, or retained cache data grows without a justified bound.
Preserve raw/cooked template distinctions, bind order, fragment identity rules, and mutable bind-value semantics.
A warm parse cache is already present; do not claim a new cache removes parsing that was not occurring.

### H3. Resolve built-in type dispatch once per result column

**Evidence:** `preparePgRowProjector` resolves a database type once, but its decoder closure calls `policy.decode` for every cell.
The built-in decoder canonicalizes that type on every non-null call. [S12], [S16]

**Hypothesis:** a prepared built-in decoder reduces repeated type-name normalization and branch selection for large or wide results.

**Experiment:** profile narrow and wide positional results at 1, 10, 1,000, and 10,000 rows.
Include integers, exact decimals, text, JSON text, temporal text, nulls, and a custom policy.
Separate projector setup from projection and include setup in end-to-end comparisons.

**Reject if:** setup cost outweighs savings, or improvements require bypassing a custom policy's per-value calls.
Retain exactness errors and all profile-specific checks. Cross-query metadata caching is not assumed safe merely because SQL text matches.

### H4. Avoid unnecessary executor setup on pooled acquisition

**Evidence:** each `createPgPoolProviderFor.acquire` calls `createPgExecutorFor` after `pool.connect`.
That setup resolves profiles, obtains policy metadata, creates parser overrides, and constructs method closures. [S10], [S13], [S16]

**Hypothesis:** stable configuration work can move out of repeated acquisition without changing physical-client ownership.

**Experiment:** compare direct execution, pooled execution, and a pinned session using the same SQL and connection count.
Measure pool acquisition separately from wrapper initialization. Count physical-client identities and executor creations in an untimed diagnostic run.

**Reject if:** native pool waiting dominates and wrapper work has no repeatable effect.
Any reuse must preserve release-once behavior, discard handling, client-specific parser fallback, and option semantics.

### H5. Preserve synchronous schema work without unnecessary async transitions

**Evidence:** `validateRow` is async and awaits the validator. `processRows` awaits it once for each attached schema and row. [S11], [S15]

**Hypothesis:** synchronous Standard Schema validation can avoid some async transitions while retaining the asynchronous path.

**Experiment:** compare no schema, synchronous identity validation, asynchronous identity validation, and two chained schemas.
Vary result cardinality and include failures at the first and last row.

**Reject if:** improvements are not repeatable, or row order, thenable behavior, failure stage, or release-before-mapping behavior changes.
Do not parallelize schema calls as a substitute for measuring this hypothesis.
