SQLBraid는 경계가 좁은 파이프라인입니다. 이것은 의도한 설계입니다.

- SQL text는 그대로 보입니다.
- value는 value로 유지됩니다.
- adapter는 물리 transport를 소유합니다.
- runtime은 connection과 scope의 correctness를 소유합니다.

## 네 개의 실행 계층

1. **`@sqlbraid/core`**는 인터페이스를 정의합니다: logical statement, binding SPI, executor/provider SPI, runtime API, representation policy, observer, capability, routine, public error.
2. **`@sqlbraid/template`**은 tagged template을 frozen `Query`로 만듭니다. 명시적인 SQL structure를 transport와 무관한 `RenderedStatement`로 rendering합니다.
3. **`@sqlbraid/runtime`**은 lease, pinned scope, transaction/savepoint continuity, stream lifetime, cancellation boundary, result-kind check, application mapping을 소유합니다.
4. **Driver adapter**는 logical statement/binding description을 native driver 호출로 바꿉니다. native result를 SQLBraid 타입으로 normalize합니다.

### 반드시 기억할 invariant

```text
segments.length
===
parameters.length + 1
```

일반 `${value}` interpolation은 bind value입니다. SQL 구조가 되지 않습니다. 구조적 SQL에는 `sql.ident`, `sql.fragment`, `sql.list`, `sql.join` 같은 명시적 helper가 필요합니다. `sql.raw`는 의도적인 escape hatch입니다.

placeholder 문법은 binding/adapter 경계에서만 나타납니다. PostgreSQL은 `$1`, MySQL은 `?`, Oracle은 `:1`, SQL Server는 `@p1`을 사용할 수 있습니다. native-template transport는 다른 물리 표현을 유지할 수 있습니다.

## Runtime의 핵심 업무는 resource ownership입니다

pooled materialized query는 다음 순서로 동작합니다.

1. lease를 acquire합니다.
2. physical I/O를 수행합니다.
3. lease를 release합니다.
4. 그 다음에만 비동기 Standard Schema mapping을 수행합니다.

stream은 다릅니다. cursor/result set은 iterator cleanup이 끝날 때까지 resource를 유지합니다.

`db.session()`은 resource 하나를 pin합니다. transaction은 시작하지 않습니다. `db.tx()`는 pinned resource에서 physical transaction 하나를 시작합니다. nested transaction은 같은 resource의 savepoint입니다. 독립 transaction이 아닙니다.

root/parent handle 사용이 다른 connection으로 빠져나갈 수 있으면 SQLBraid는 그 사용을 거부합니다. 조용히 reroute하지 않습니다. transaction control이나 cleanup 때문에 connection 상태가 불확실해지면 SQLBraid는 resource를 poison/discard합니다. 낙관적으로 재사용하지 않습니다.

## Prepared, batch, bulk는 규칙이 서로 다릅니다

- `db.prepare()`는 **SQLBraid logical shape**을 고정합니다. universal server-side prepared cache를 약속하지 않습니다.
- `db.batch()`는 여러 operation을 하나의 physical use/lease에서 실행합니다. operation은 서로 달라도 됩니다. batch는 **transaction이 아닙니다**.
- `db.bulk()`는 하나의 homogeneous command shape을 여러 input에 적용합니다. adapter가 실제 bulk 전략을 선택합니다.

## TypePolicy는 application mapping이 아닙니다

`TypePolicy`는 database/native driver value를 SQLBraid의 canonical JavaScript representation으로 normalize합니다. Standard Schema는 그 canonical representation을 application/domain value로 매핑합니다. 두 경계가 분리되어 있으므로 runtime에 universal codec framework가 필요하지 않습니다.

## Tooling은 별도의 plane입니다

runtime package는 metadata, codegen, compiler, CLI, editor, Vite에 의존하지 않습니다.

- `@sqlbraid/compiler`는 source discovery/lowering을 소유합니다.
- `@sqlbraid/metadata`는 database evidence를 기록합니다.
- `@sqlbraid/codegen`은 metadata와 TypePolicy로 model을 생성합니다.
- `@sqlbraid/tooling`은 LSP/CLI/editor 기능을 위해 positive evidence를 결합합니다.

metadata에 없는 사실은 unresolved evidence입니다. 사용자 SQL이 invalid라는 증거가 아닙니다.

## 소스는 이 순서로 읽으세요

1. `packages/core/src/`: `statement.ts` (`RenderedStatement`), `query.ts` (`Query`), `binding.ts` (`StatementBindingAdapter`), `executor.ts` (`QueryExecutor`, `ConnectionProvider`), `database.ts` (`Database`), `authoring.ts` (`SqlTag`). `index.ts`는 re-export만 합니다.
2. `packages/template/src/`: `tag.ts` (`createSqlTag()`)와 `render.ts` (rendering path).
3. `packages/runtime/src/index.ts`: `createScopedDatabase()` → `prepareObserved()` → `prepare()`. 그 다음 `operations/materialized.ts`: `runPrepared()` → `leaseForUse()` → `physical()` → `finalizePhysical()` → `processRows()`.
4. runtime의 `stream()`, 그 다음 `session()`과 `tx()`.
5. 첫 reference adapter로 PostgreSQL의 `pgStatementBinding` / `createPgExecutor()`, 다음으로 resource lifecycle이 복잡한 Oracle.
6. static tooling 작업을 할 때 compiler → metadata → codegen → tooling.

contributor용 전체 walkthrough와 invariant는 저장소의 [한국어 mental model](https://github.com/Clickin/SQLBraid/blob/main/docs/mental-model.ko.md)을 참고하세요. Driver 구현자는 [드라이버 작성 가이드](/SQLBraid/ko/agents/driver-author/)도 읽어야 합니다.
